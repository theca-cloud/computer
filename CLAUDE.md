# This repo: `computer`

Theca on computers (desktops, laptops, servers): one crate and binary, `theca` (ADR 0004): the CLI and daemon; the Tauri app behind the `gui` feature; the sync client and the drive (ADR 0008). Built on `theca-client` (from `core`). A second crate, `fileprovider/` (a workspace member), is macOS's File Provider extension and the app's File Provider calls: every `unsafe` call lives there, `theca` keeps `forbid(unsafe_code)`.

- `src/plan.rs` is reconciliation, pure: base, local scan and remote states in, actions out. Every rule of `decisions.md` (Sync) has a unit test there.
- **`core` is pinned to a release tag** (`Cargo.toml`, from its GitHub mirror), and `scripts/ci.sh` builds the test server from those same sources (found through `cargo metadata`). To work against an unreleased `core` during a sprint, put in an untracked `.cargo/config.toml` (not `Cargo.toml`, which then stays committable): `[patch."https://github.com/theca-cloud/core"]` with `theca-client = { path = "../core/crates/client" }` and `theca-common = { path = "../core/crates/common" }`. `Cargo.lock` then records the patch: commit it only once the release is pinned. The test server comes from those sources too.
- **`USING.md` is the users' page, theca.rs/computer** (rendered by `saas` at its pinned `COMPUTER_VERSION`): a sprint that changes how the app is installed, updated, signed or used (a channel, a flag, an exit code, the keychain) rewrites it in the same change, and the release is followed by a bump of `COMPUTER_VERSION` in `saas`. Its tests only check the exit codes and environment variables.
- **`ops::MIN_SERVER`** is the oldest server (its `core`, and the CE shipping it) the client works with: raise it when the client starts using an API a server gained, never with each `core` release; `USING.md` says the same.
- `src/state/` is the only SQL: one SQLite file, forward-only since 1.0. A schema change is `SCHEMA` and a new step in `src/state/migrations/` (never an edited one: `scripts/ci.sh` refuses it); `tests/upgrade.rs` reads every release's state back and compares the schemas.
- App passwords live in the OS keychain (`keychain.rs`). Tests never touch a developer's: `common::keychain()` takes the in-memory store unless `THECA_TEST_KEYCHAIN=os` (GitHub's macOS and Windows runs); a test starting a child `theca` uses `device_without_keychain` (on macOS, another binary reading the entry prompts and hangs).
- The scenarios run in parallel in one process, each against a server of its own, on every platform (a port from `common::free_port`, never `bind(0)` alone). `converge` means the server matches the folders, not that the engines' rounds ended: the engine's state (notices, entries) is read with `eventually`.
- `scripts/ci.sh` runs on Windows too (Git Bash, on GitHub's runner): paths from Cargo come as `C:\\…`, Git Bash's `pwd` gives `/d/…` (`pwd -W` for a Windows one), binaries end in `.exe`.
- **A test run alone needs the test server** at `target/debug/theca-server` (a `cargo clean` removes it): `scripts/ci.sh test` builds it, or `SQLX_OFFLINE=true cargo build --manifest-path <core's sources> --target-dir target -p theca-core` (the path as `scripts/ci.sh` finds it), or `THECA_SERVER`. `tests/crash.rs` runs only with `--features crash-points`.
- A new test of a guard is checked failing with the guard removed, before it counts: sprint 11 had three that passed without theirs.
- A quick `cargo check --all-targets` skips `gui.rs`: check `--features gui,custom-protocol` too (sprint 13 broke the app build that way). A change to what the GUI sends the page (`PairView`, `Update`) is a change to `ui/src/lib/app.svelte.ts` and its components: grep the page for the old field or string.
- A flag read from the environment (`env = "…"`) takes `value_parser = clap::builder::FalseyValueParser::new()`: the default bool parser refuses `X=1`. Run a new flag or variable once from a shell, as `USING.md` documents it.
- `cargo mutants` copies the tree to `$TMPDIR` and builds it there (a second `target/`, GBs): delete its `cargo-mutants-…` copy and `mutants.out/` once read. With the local patch above, the copy can't find `../core`: run it `--in-place` (it restores the file; check `git status`). A day of test runs grows `target/` past 10 GB: `cargo clean` past ~5 GB.
- Tests mounting a disk image (macOS, `hdiutil`) hold it in a guard that detaches on drop (`Mounted`, tests/safety.rs): a failing test left images attached.
- **A drive scenario (FUSE, Linux) deadlocking in its own mount can't be killed**: a thread waits uninterruptibly on the process's own FUSE answer, the process stays a zombie, and its test server lives on, holding Postgres connections until later runs fail with "too many clients" (`kill -9` the `theca-server` processes). Run them under `timeout`, and stop a drive device before its test folder is removed (deleting through the mount waits on the same process). Without `/dev/fuse` and `fusermount3` they skip; `THECA_TEST_DRIVE=1` makes that a failure (GitHub).
- **A drive is OS-specific underneath** (`src/drive/`): FUSE on Linux (`fuse.rs`, a backing folder in the data dir, placeholders marked by an extended attribute), Cloud Files on Windows (`cloud.rs`), the File Provider on macOS (`provider.rs` answers the extension, portable and tested everywhere). Windows and macOS code doesn't build here: `cargo clippy --target x86_64-pc-windows-gnu` (MinGW) and `--target aarch64-apple-darwin` (zig as the C compiler, `CC_aarch64_apple_darwin`) catch most of it in a container; the rest is GitHub's runners.
- **A placeholder's identity is its file ID**, never its path (`plan::is_another`): it can't be an atomic save, so one renamed over another is that one moved. Code finding a drive's file by path (a fetch, an eviction) checks the file ID, or checks again once it holds the file (`drive::evict_synced`).
- **macOS refuses to evict what it still holds as kept** (`NonEvictable`, -2008) until it has read the item again after an un-keep: signal, then retry (`ops::free_on_mac`). Nothing but a real Mac shows it: `tests/mac_drive.rs` on GitHub's runner.
- **A real Mac** (the developer's, between GitHub runs): `ci/mac/` copied to `~/mac-check` with a bundle of the branch (`git bundle create ~/mac-check/computer.bundle <branch>`), carried with `rc cp` both ways; `ci.sh test --drive mac_drive` is the macOS job, `drive-check.sh <dmg>` the installed app with Finder's actions. Traps met there: an app copied in by a script while quarantined is translocated (its drive refused, -2002); a shell listing a drive in its first seconds gets "Operation not permitted" until the app serves it (retry, don't diagnose a permission); a fix to macOS-only code is unproven until that Mac ran it (clippy for `aarch64-apple-darwin` only compiles it).
- **`scripts/release.sh` in this workspace** runs `scripts/ci.sh` natively, which needs WebKitGTK (not installed here): run it in the CI image (`git.pband.ch/theca/ci-computer`), with `git-cliff` mounted in, `gh` replaced by a script printing the real `gh run list -R theca-cloud/computer -w test.yml -b dev -L 1` answer taken just before, and `url./src.insteadOf=<origin>` (`GIT_CONFIG_*`) so its tag fetch needs no SSH key; it stops at the commit (no GPG key in the container): finish its last steps outside (`git commit -m X.Y.Z`, `git tag -a`, `git checkout dev && git merge --ff-only prod`).
- A push to the scratch GitHub repo goes to its URL, never the clone's `origin` (the local repo); check a run's head SHA before reading it as the new commit's.
- **Logs** (`src/logs.rs`): every process appends to `<data dir>/logs/theca.<day>.log`, each line under its spans (`command`, `account`, `pair`, `round`, `fetch`, `request`); a user's problem starts there (`theca logs` names the folder, `--level debug` for more). Log a path or a count, never an argument (`login --token`) or an `Account`. A command's outcome goes to the target `logs::EXIT` (the file only: the command prints it).
- The app tests (`tests/app.rs`) take turns (`ONE_APP`): the app is single-instance, a second launch hands over to the first and exits.
- The drive's scenarios need their backend: `/dev/fuse` and `fusermount3` (Linux), an installed Theca.app with its extension (`THECA_TEST_MAC_APP`, `ci/mac-app.sh`); without it they skip, `THECA_TEST_DRIVE=1` makes that a failure (GitHub). On Windows a placeholder shows a moment before its entry is recorded: a test waits for the entry, not only the file.
- `tauri build` (`ci/package.sh`) rewrites `tauri-build`'s line in `Cargo.toml` (`features = []`): harmless, not committed.

## Workflow differences

- **CI in two systems** (ADR 0005): Woodpecker checks Linux on every push; GitHub Actions tests macOS, Windows and Linux arm64 from `dev`, and, on a tag, runs those tests again, then builds the packages and the release. Check GitHub with `gh run list -R theca-cloud/computer` (`ci/README.md`), not only `woodpecker-cli`.
- **`dev` is mirrored to GitHub** (public) once Woodpecker's checks pass; feature branches stay on Gitea.
- **`scripts/release.sh`** also checks GitHub's latest `dev` test run; the release itself (packages, GitHub release) happens on GitHub after the tag is pushed. No Gitea release.
